# 工程技能规范

以下规则在每次编码交互中自动生效。来源: Matt Pocock skills-for-ai 仓库，适配本项目。

---

## 1. 诊断 (Diagnose)

遇到 bug 或性能问题时，遵循严格的诊断流程：

1. **构建反馈循环** — 最重要的一步。找到一个快速、确定性的通过/失败信号（失败测试、CLI 脚本、最小复现）。没有反馈循环就不要猜测原因。
2. **复现** — 运行循环，确认看到的是用户描述的那个 bug，不是别的。
3. **假设** — 生成 3-5 个有排序的假设，每个必须可证伪（"如果 X 是原因，那么改 Y 会让 bug 消失"）。
4. **验证** — 每次只改一个变量。优先用断点/REPL，其次定向日志（带唯一前缀如 `[DEBUG-xxxx]`），绝不"全部打印再 grep"。
5. **修复 + 回归测试** — 先写回归测试再修复。修复后重跑反馈循环。
6. **清理** — 删除所有调试代码，提交信息中说明根因。

**如果一个方法失败两次，停下来诊断根因，换一个根本不同的方法。**

---

## 2. 代码质量原则

### 深模块 (Deep Modules)
- 追求"小接口、深实现"：调用者只需知道很少的东西，模块内部封装大量复杂性。
- **删除测试**：想象删掉一个模块。如果复杂性消失了，它是透传层（浅模块）；如果复杂性散布到 N 个调用者，它在发挥作用（深模块）。
- 浅模块（接口和实现一样复杂）是重构信号。

### 接口设计
- 接口 = 调用者必须知道的一切（类型、不变量、错误模式、顺序、配置），不只是函数签名。
- 测试应该通过公共接口验证行为，不测试实现细节。

---

## 3. 增量开发 (Vertical Slices)

**禁止水平切片**（先写所有测试再写所有实现）。

正确做法：垂直切片，一次一个功能点：
```
RED→GREEN: test1→impl1
RED→GREEN: test2→impl2
...
```

每个测试响应上一个循环学到的东西。

---

## 4. 原型 (Prototype)

原型是**回答一个问题的一次性代码**：
- 逻辑问题 → 最小可运行的终端脚本
- UI 问题 → 多个变体方案

规则：
- 一条命令就能跑
- 不要持久化（除非问题本身就是关于持久化的）
- 跳过打磨（不要测试、不要错误处理、不要抽象）
- 完成后删除或吸收，不要留在仓库里腐烂

---

## 5. 架构改进

发现架构摩擦时：
1. 探索代码库，注意哪里理解一个概念需要跳转多个小模块
2. 找到浅模块（接口和实现一样复杂的地方）
3. 提出"加深"方案：把复杂性集中到一个模块后面
4. 用 locality（变更集中在一处）和 leverage（调用者获得的便利）来评估

---

## 6. 沟通风格

- 技术内容保持精确，废话删掉
- 不确定时主动问，不要猜
- 给出建议时说明理由
- 如果用户说"grill me"，对方案进行严格追问，逐个分支走决策树
- 如果用户说"zoom out"，退后一层抽象，给出模块地图和调用关系

---

## 7. 交接 (Handoff)

当对话需要交接时：
- 总结当前状态、已做决策、未解决问题
- 引用已有文档（不重复内容）
- 建议下一步使用的技能/方法
