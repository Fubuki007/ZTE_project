## 1. 背景：这个项目在做什么

### 一句话概括

用 5G 基站的天线阵列做"雷达成像"——同时完成通信和感知。

### 通俗类比：盲人用拐杖走路

你看不见路（不知道目标在哪），但你可以：
1. 发出一声喊（发射 OFDM 信号）
2. 听回声（接收反射信号）
3. 根据回声回来多快判断距离，根据左右耳听到的时差判断方向

**问题在于**：在你喊的时候，你自己的耳朵也听到了——这叫**自干扰**。如果你的喊声太大，回声就听不见了。

这个项目的核心就是：**如何在自干扰存在的情况下，精确判断目标的角度、距离和速度。**

### 需要满足的指标

| 指标 | ZTE 要求 | 
|------|---------|
| 频段 | 24.25-29.5 GHz（毫米波） |
| 感知距离 | 水平 500m，垂直 600m |
| 精度 | 分米级（<0.1m） |
| 刷新率 | **< 1 秒** |

### 数据规模

接收信号是一个 4D 数组：`8×8×12672×256`

什么意思？
- 8×8 = 64 根接收天线（像一个 8×8 的方阵）
- 12672 = 每根天线收到 12672 个"频率样本"（对应不同距离）
- 256 = 每个频率样本被采集了 256 次（对应不同速度）

总共 **2.08 亿**个复数数据点。太大了。

## 2. 优化一：速度优化

### 2.1 一开始有多慢？

最初版本的估计器（`joint_estimator_fast.m` 原版）运行一次需要 **4.9 秒**。

可以想象成：你要在 2.08 亿本书里找两本特定的书，每本都要翻开读一遍——太慢了。

### 2.2 为什么会慢？找到了瓶颈

用一个叫"profiling"的工具分析后发现，**81.8% 的时间花在了一件事上**：

```matlab
% 对每根天线的每个频率样本，逐一乘以发射信号
for 每一根天线:
    for 每个频率:
        for 每个时间点:
            接收信号 × 发射信号的共轭  ← 这个操作重复了 2.08 亿次
```

这就是"信道均衡"——相当于你对 2.08 亿本书，每本都做了一次同样的翻页动作。

### 2.3 关键发现：可以调换顺序！

数学上有一个重要的性质：

```
(接收信号1 + 接收信号2 + ...) × 发射信号
= 接收信号1 × 发射信号 + 接收信号2 × 发射信号 + ...
```

但发射信号对所有 64 根天线是**一样的**！所以我们可以：

```
旧方法:  先做 64 次均衡（2.08 亿次乘法），再求和
新方法:  先求和（只用 3.2M 次加法），再做 1 次均衡（3.2M 次乘法）
```

### 2.4 类比：点菜

想象你是餐厅老板，要给 64 个顾客每人算账：

| 方法 | 做法 | 工作量 |
|------|------|--------|
| 旧方法 | 每道菜 × 单价 → 每顾客求和 | 大 |
| 新方法 | 先算总份数 → 总份数 × 单价 | 只有旧方法的 1/64 |

因为单价对所有人是一样的——就像发射信号对所有天线是一样的。

### 2.5 代码对比

#### 优化前（逐天线处理，慢但直观）

```matlab
for l = 1:L  % 对每个时间点
    for mx = 1:Mx  % 对每根 X 方向天线
        for my = 1:My  % 对每根 Y 方向天线
            rx_cube(mx,my,:,l) = rx_cube(mx,my,:,l) .* conj_tx(:,l);
            %   ↑ 64根天线 × 12672频率 × 256时间 = 2.08亿次操作
        end
    end
end
s_sum = squeeze(sum(sum(rx_cube, 1), 2));  % 所有天线求和
```

#### 优化后（先求和再均衡，快但数学等价）

```matlab
% 先空间求和：把 64 根天线的信号加起来
rx_sum = squeeze(sum(rx_cube, [1 2]));   % (8,8,12672,256) → (12672,256)
%   ↑ 只有 3.2M 个元素了！

% 再做均衡：只对 3.2M 个数据做一次乘法
rx_eq_sum = rx_sum .* conj(tx_norm);      % (12672,256) × (12672,256)
```

### 2.6 为什么数学上等价？

因为：`conj(tx_signal)` 不依赖天线索引（mx, my）。

对于固定的频率 n 和时间 l，64 根天线收到的信号共享同一个 `conj(tx_signal(n,l))`。所以：

```
∑_{mx,my} [ rx(mx,my,n,l) × conj_tx(n,l) ] 
= [ ∑_{mx,my} rx(mx,my,n,l) ] × conj_tx(n,l)
```

本质上是乘法对加法的分配律。

### 2.7 速度变化一览

```
原始版本:     4.9 秒    (逐天线逐频率循环)
  ↓ 先求和再均衡
v3 快速版:    0.26 秒   (快 19 倍！但精度没变)
  ↓ 增加精度（ESPRIT增强、补零、加窗）
v4 工程版:    0.93 秒   (目标 0.7-0.9s，精度大幅提升)
```

### 2.8 v4 进一步增加了哪些精度提升？

有了 0.26s 的"时间余量"（离 1s 要求还剩 0.74s），我把余量"兑换"成了精度：

| 改动 | 通俗解释 | 精度收益 |
|------|---------|---------|
| **ESPRIT 采样增强** | 原来用 1.2 万个点估角度，现在用 26.2 万个点 | 角度误差降低约 5 倍 |
| **多普勒补零 2 倍** | FFT 后面填零（不花钱的插值），速度分得更细 | 速度误差从 0.58 m/s → 0.03 m/s |
| **2D Hann 窗** | 像给镜头加滤光片，抑制"鬼影"（旁瓣） | 旁瓣降低 32dB |
| **双轮插值** | 抛物线算一遍，再加重心法微调一遍 | 距离误差从 0.027m → 0.008m |

### 2.9 最终性能

| 指标 | 优化前 | 优化后 | 验收要求 |
|------|:-----:|:-----:|:------:|
| 耗时 | 4.9 s | **0.93 s** | < 1 s ✅ |
| 角度误差 | 0.007° | **0.000°** | 分米级 ✅ |
| 距离误差 | 0.027 m | **0.008 m** | < 0.1 m ✅ |
| 速度误差 | 0.577 m/s | **0.030 m/s** | — |

## 3. 优化二：算法修正

### 3.1 问题：预编码器在自干扰变大时崩溃

项目中有三种预编码方案（用不同的方法解决自干扰问题）：

| 方案 | 通俗解释 |
|------|---------|
| **ZF** | 只考虑通信，完全不管自干扰（最简单的） |
| **Nullspace** | 让发射信号"绕开"自己的接收天线 |
| **Lagrange** | 在通信质量和自干扰抑制之间找最优平衡 |

### 3.2 崩溃现象

当我跑系统对比测试时，发现 lagrange 方法在自干扰变大时，**角度估计完全崩溃**：

```
自干扰强度     →    角度误差

scale=0    (无干扰)   →   0.04°   ✅ 正常
scale=1    (轻微)     →   0.04°   ✅ 正常  
scale=10   (中等)     →   0.04°   ✅ 正常
scale=100  (较强)     →   29.2°   ❌ 崩溃！角度完全错了
scale=1000 (强干扰)   →   43.5°   ❌ 错得离谱
```

### 3.3 根本原因：矩阵"病态"

lagrange 方法需要计算一个矩阵的逆：`inv(H_SI^H × H_SI)`

可以理解成：你要翻一块木板，但木板几乎和你的力量方向垂直——无论你怎么用力都翻不动。这就是"矩阵接近奇异/病态"。

自干扰信道矩阵 `H_SI` 在数学上有非常小的奇异值，导致求逆时数值爆炸。

### 3.4 修复：自适应正则化

类比你推一块很重的石头：

```
错误做法:  直接推 → 推不动 → 滑倒
正确做法:  先垫一块楔子（一点点帮助），再推 → 就推得动了
```

在数学上，这个"楔子"叫**正则化**——给矩阵加上一点点"虚拟刚度"：

```matlab
% 修复前（硬求逆，自干扰大时数值爆炸）
R = H_SI' * H_SI;
Rinv = inv(R);                    % R 可能接近奇异
W = Rinv * H_c / (H_c' * Rinv * H_c);

% 修复后（自适应正则化，自动加楔子）
R_raw = H_SI' * H_SI;
lambda = 0.001 * trace(R_raw) / Nt;   % ← 自适应：自干扰越强，楔子越大
R = R_raw + lambda * eye(Nt);         % ← 加楔子（对角加载）
Rinv = R \ eye(Nt);                   % 数值稳定求逆
```

关键改进：**正则化强度 `lambda` 不是固定值，而是随自干扰强度自适应**。

- 自干扰弱时：`lambda` 小 → 几乎不影响最优解
- 自干扰强时：`lambda` 大 → 防止矩阵病态，保持数值稳定

### 3.5 修复前后对比

```
             修复前                      修复后
scale=0:     θ_err=0.04°  ✅           θ_err=0.04°  ✅
scale=1:     θ_err=0.04°  ✅           θ_err=0.04°  ✅
scale=10:    θ_err=0.04°  ✅           θ_err=0.04°  ✅
scale=100:   θ_err=29.2°  ❌           θ_err=0.04°  ✅
scale=1000:  θ_err=43.5°  ❌           θ_err=0.04°  ✅
```

### 3.6 零空间法也修了同样的问题

Nullspace 方法在处理"零空间投影"时也遇到了类似的矩阵病态问题，用同样的自适应正则化修复：

```matlab
% 修复前
c = pinv(H_SI_Nc) * (H_SI * W0);   % 硬求伪逆

% 修复后
Gram = H_SI_Nc' * H_SI_Nc;
lambda = 0.001 * trace(Gram) / dim_Nc;      % 自适应
c = (Gram + lambda * eye(dim_Nc)) \ (H_SI_Nc' * H_SI_W0);  % 正则化求解
```

## 4. 为什么这两个修改是正确的

### 4.1 速度优化为什么正确

| 质疑 | 回答 |
|------|------|
| "先求和再均衡会不会丢失信息？" | 不会，因为 `conj(tx)` 对所有天线相同，乘法分配律保证数学等价 |
| "这是不是偷懒取巧？" | 不是，这是标准雷达信号处理中的"非相干积累"，所有商用电达都用 |
| "实际硬件能做到吗？" | 能，FFT/求逆/CORDIC 相位提取都有成熟的 FPGA IP 核 |

### 4.2 正则化纠正为什么正确

| 质疑 | 回答 |
|------|------|
| "加正则化是不是在改原算法？" | 不是改，是**补全**。原论文公式中的 `R^(-1)` 隐含要求 R 可逆，但实现时必须考虑数值稳定性 |
| "加正则化会不会影响精度？" | 自干扰弱时 `lambda` 自动变小，影响 <0.01°；自干扰强时虽然牺牲一点最优性但换来了稳定性——稳远比"最优但不稳"有用 |
| "实际工程中这是标准做法吗？" | 是，Tikhonov 正则化/对角加载是所有矩阵求逆算法的标准实践，雷达、通信、图像处理都在用 |

### 4.3 一句话总结

> **速度优化**利用"先求和再均衡 = 先均衡再求和"的数学等价性，将 208M 元素的遍历降到 3.2M，提速 19 倍后又把余量兑换成了精度。
>
> **算法修正**用自适应正则化填补了原公式的数值漏洞——就像给精密的锁加润滑油，让它在自干扰大的时候也能正常工作。
